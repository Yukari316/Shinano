# Shinano.Infrastructure 约定

通用约定与高频硬规则见仓库根目录 `AGENTS.md`；本文件记录数据库、RustFS、聊天归档与日志的完整规格。

## PostgreSQL

- 使用 PostgreSQL 与 SqlSugar，重新设计表结构。数据读写优先使用 SqlSugar 的实体 API（Queryable、Insertable、Updateable、Deleteable、CodeFirst）；只有 SqlSugar 无法表达或无法保证正确性时才手写 SQL（如分区与目录 DDL、`on conflict`、`for update skip locked`、`returning`），并在该语句前添加以 `SQL_NEED:` 开头的注释说明原因。手写 SQL 中的值一律参数化，只有经校验的标识符与 DDL 中不能参数化的强类型值可以拼入语句。
- 使用 `global` 存放全局数据，使用 `user_<self_id>` 存放机器人账号数据；插件按数据是否属于账号选择 schema。机器人账号与群成员身份不得混淆。
- 插件表名以插件标识为前缀（ID 中的 `-` 换成 `_` 后加 `_`，如 `image-search` 为 `image_search_`），只含小写字母、数字与 `_`，不超过 63 个字符；插件在 `plugin.json` 的 `tables` 中按 `global` 与 `account` 两组写出用到的全部完整表名，加载时校验前缀，清除插件数据时只删除这些表。插件的表只由带 `[SugarTable]` 的实体经 CodeFirst 创建，不手写建表、不用动态表名或分表；本仓库的原生插件遵守此约定，第三方插件不做核对。启动时由 SqlSugar CodeFirst 创建缺失的表并补齐新增可空列；删列、改类型、改名等破坏性变更由插件提供带版本号的显式迁移，宿主在版本表中记录各插件结构版本并按序执行，失败时该插件不启用。
- 切换账号后保留宿主及插件通用配置、启用状态与可复用媒体；有人问、B站订阅、聊天记录和统计按账号隔离。旧账号记录继续按当前部署保留配置清理，切回时恢复仍有效的数据。
- 数据库离线期间消息无法入库，故障区间先记录在内存，恢复后写入归档缺口记录并在管理面板显示。
- Bot 初始化时检查并创建缺失的 schema 和表。数据库本体、角色和扩展的创建属于管理员初始化流程，不能默认为 Bot 日常权限。
- 数据库连接通过部署配置中的 DSN 指定。开发与测试使用测试库 `shinano_debug`，正式部署使用 `shinano`；地址见 `agent_tmp/docs/environment.md`。
- 数据库由管理员初始化脚本创建及授予 `shinano` 业务角色（数据库归管理员所有，业务角色获授 `CONNECT`、`CREATE`、`TEMP`，不创建扩展）；Bot 使用业务角色运行，不能使用 PostgreSQL 超级用户账户。
- 数据库编码为 UTF8。根据实际查询与可用扩展选择索引和类型，不因扩展已安装而引入无用途依赖；扩展兼容性和权限需核实。
- 开发与测试只在 `shinano_debug` 中创建 schema、表与分区，集成测试使用按运行生成的 schema 并在结束后删除；不创建角色、数据库或扩展，不清理他人创建的数据。

## RustFS 与媒体

- RustFS 是 Bot 的基础设施服务，用于持久化图片、音频和文件；启动时检查可用性，不可用时明确报错。
- 运行中 RustFS 离线不停止全部功能：聊天媒体按归档规则标记缺失，需要媒体存储的功能直接报错；故障开始和恢复时各通知 Super User 一次。
- RustFS 的地址与密钥由部署配置提供（开发环境见 `agent_tmp/docs/environment.md`），经 S3 协议访问；不把凭据内容写入工作文档、日志或可提交配置。
- 一个 Bot 部署通常只有一个进程和一个当前 `self_id`；进程停止后可以切换为另一个账号而不改变其余配置。Bucket 前缀默认 `shinano`，本地测试配置为 `shinano-debug`，用户可自定义。每个 Bot 部署必须使用唯一前缀，不支持多个部署共用 bucket，对象 key 不附加部署命名空间。
- 媒体分三类生命周期，同一部署切换账号后均可复用：
  - 聊天媒体：存于 `<prefix>-chat`，随聊天记录过期清理。
  - 持久媒体：存于 `<prefix>-media`，由宿主文件服务统一管理，按内容去重。每个使用方登记引用记录（插件、业务键、账号），插件只增删自己的引用，不直接删除对象；最后一条引用删除后经宽限期（默认 24 小时）再物理删除。插件停用保留引用，管理员清除插件数据时才删除其引用。QA 回答媒体和功能需要长期保存的聊天媒体属于此类。
  - 插件独立媒体：插件持有的独立 bucket（`<prefix>-<用途>`），对象不来自聊天，由插件自行管理生命周期，不使用引用记录。宿主提供插件完全控制自有 bucket 的接口：创建与删除 bucket，写入、读取、列出、查询元数据与删除对象，生成 IM 可下载的临时链接；用途名在插件间不得重复，存储客户端只能访问该插件自己的 bucket。管理员清除插件数据时经二次确认清空并删除其 bucket。Hso 图库属于此类。
- 测试与正式部署的保留配置独立。
- 向 IM 实现端发送媒体时使用预签名 GET 直链，默认有效期 10 分钟，可配置；单独配置 IM 端可访问的 RustFS 地址，默认等于内部地址；不开放 bucket 公共读。LLBot 到 RustFS 的实际连通在实现阶段验证。
- 持久化文件大小上限可配置，单位 MB（1024×1024 字节），默认 100 MB，适用于聊天媒体与持久媒体；插件独立媒体使用不高于全局值的插件上限。消息段带声明大小时下载前检查，下载中按实际字节计数，超限立即中止。
- 开发与测试只使用 `shinano-debug` 前缀的 bucket，集成测试使用按运行生成的 `shinano-debug-test-*` bucket 并在结束后删除；不删除其他 bucket 或对象。

## 聊天记录与统计

- 保存完整聊天正文，避免依赖 LLBot 自身保存的历史记录，为后续 LLM 群聊总结提供数据；LLM 总结本身不自动纳入当前实现范围。
- 只保存 Sora 可支持的消息段序列化结果，不保存原始协议报文；存储格式尽量减少数据库空间占用，避免大数据量下的性能问题。
- 纯文本消息只存可见文本；含其他消息段时额外存精简段 JSON，媒体只存聊天媒体整数 ID。会话与发言者只存整数 ID，不保存群名、昵称等可变信息，需要时通过 Milky 实时获取。
- 聊天表按自然日分区，过期时删除整个分区。自然日按部署配置的时区计算（默认 `Asia/Shanghai`，与统计共用），分区由宿主以显式 SQL 维护；修改时区只影响此后新建的分区，已有分区不重建，切换当天的分区可能不足或超过 24 小时。段 JSON 列使用 lz4 压缩，要求 PostgreSQL 18 及以上（初始化时核验版本、编码与 lz4）。
- 聊天媒体持久化到当前 Bot 部署的聊天媒体 bucket，内容相同的媒体允许复用；图片、音频、视频和文件分别计数。字数按用户可见字符计数，汉字、字母、数字、标点和完整 emoji 计入，空白及媒体不计入字数。
- 聊天记录默认保留 30 天，可通过配置修改，过期后清理对应聊天媒体；业务所需的长期媒体副本按各自用途独立保留。过期清理（聊天分区、发言统计、聊天媒体、宽限期已过的无引用持久媒体）在每次启动时执行一次，之后每小时一次，避免调试或短时运行的进程一直不清理；每次执行都以 Information 记录数据库与 bucket 的删除数量（删除为 0 时同样记录），逐个对象的删除记 Debug。
- 支持按不同发言者统计发言条数、字数等信息，按“会话 × 发言者 × 自然日”聚合，日期边界使用配置时区（默认 `Asia/Shanghai`），原始消息按 UTC 存储。Bot 成功发送的消息作为一个发言者计入，管理面板默认筛除并可切换显示。统计结果独立持久化，默认永久保存；可选的定时清理按“保留最近 N 天”配置。
- 记录群聊和私聊，包含视频、合并转发等消息类型。接收的自身消息全部排除，不参与记录、统计和业务处理；Bot 自己的聊天内容以成功发送的请求为准记录。
- 宿主通过 Sora 的 `UseMessageRecorder` 登记唯一的消息记录器，取得全部收到的聊天消息（包括被连续对话消费、被 Filter 拦截的消息）和经 Sora 发送 API 成功提交的消息，统一处理消息身份、去重、正文、媒体归档和发言统计。插件直接使用 Sora 原生回复与连续对话，不调用归档接口。记录器只把记录转入宿主后台处理，不在 Sora 记录队列上执行入库或下载。宿主归档缓冲容量可配置；缓冲已满时丢弃新记录，该区间登记为归档积压类型的归档缺口，开始和恢复时各通知 Super User 一次。
- 媒体按消息段出现次数计数，同一图片出现两次计两张，与文件存储去重分开。引用与合并转发中的历史内容保留，但不重复计入当前发言者新增的字数或媒体数。
- 聊天媒体超限或下载、上传失败时保留正文及媒体元数据，明确标记缺失并告警，不把归档不完整的记录报告为完整。LLBot 断线期间未上报的消息无法补回，断线区间与数据库离线区间一样登记为归档缺口，不通过拉取历史消息补齐。

## 日志

- 使用 Sora 自带日志实现，并持久化到启动目录下的 `Logs`，目录不存在时自动创建。文件名为 `<日期>-<启动时间>.log`，同一天多次启动不互相覆盖。
- 默认日志等级为 Info，可配置，修改后重启生效。
- `Logs` 总大小超过阈值时，从修改时间最早的文件开始删除，直到低于阈值；当前进程正在写入的文件不删除。阈值可配置，默认 2 GB。
- 管理面板的实时日志订阅内存日志流，历史日志从文件读取。
